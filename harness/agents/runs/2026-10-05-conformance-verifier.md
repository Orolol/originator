## Prompt (verbatim)

You are the **verifier** in `/home/orosius/workspace/originator`. Another agent is concurrently implementing a **clone** (in `clone/`) of Hugging Face's "gated models" access-request backend: an in-memory, deterministic server that must reproduce the real Hub's behaviour over the same wire protocol. Your job is to build an **independent, black-box conformance suite** that proves (or disproves) that the clone behaves like the real Hub — using the recordings we made on the real Hub as ground truth.

**You must stay blind to the implementation**: do NOT open any file under `clone/` except `clone/README.md` (if it exists) and `clone/pyproject.toml` (to know how to start it). Derive every expectation from the spec and the recordings, never from the clone's code. This independence is the point: tests that agree with the code by construction prove nothing.

## What to build: `conformance/` (uv project, Python 3.12)
- `conformance/pyproject.toml` (deps: pytest, httpx, huggingface_hub, pyyaml if you want), `uv python pin 3.12`, `uv sync`. Config: `BACKEND_URL` (default `http://127.0.0.1:8200`).
- **Replay harness** (`conformance/src/conformance/replay.py` or similar): loads a recording, maps it to the backend under test (URL origin `https://huggingface.co` or `http://127.0.0.1:8100` → `BACKEND_URL`; identities: `HF_OWNER_ACCESS_TOKEN`/`OWNER`/persona `owner` → `persona-owner`, `HF_REQUESTER_ACCESS_TOKEN`/`REQUESTER`/`requester` → `persona-requester`, `BAD_TOKEN` → an invalid token, `anonymous` → no header), sets the clone to the recording's **initial state** via `PUT /__clone__/state` (you write these initial-state seeds yourself from what the recordings show at their first steps — e.g. owner-walkthrough starts with NO request on the sandbox repo; the completion run starts with TestingBOrig pending at `2026-10-05T14:17:07.311Z`; the UI walkthrough starts in `reset`), replays every request in order (skip `wait`), and compares each response to the recording with documented **normalisations** only for legitimately volatile things (timestamps → check presence/ordering/relations instead of values, e-mails → `<email>` (recordings are redacted), ETag of JSON responses, Content-Length, `Location` origin). Everything else must match exactly: status, `X-Error-Code`, `X-Error-Message`, `Content-Type` family, JSON body structure/keys/key order/values, text bodies, `Location` path, `Content-Disposition`.
- Produce a per-step diff report (machine-readable + Markdown) and a summary per scenario. Write a small CLI `uv run --project conformance conformance-report --out docs/hf-gated/conformance-report.md` … actually **do not write into docs/** — write the report to `conformance/reports/latest.md` (and `.json`); the orchestrator publishes it.
- **Known divergences file** `conformance/divergences.yaml`: each accepted mismatch = scenario, step id, field, rule ID / Q-id, reason ("clone provisional choice", "recording artefact", …). Tests fail on any mismatch NOT listed there. Start it empty; only add entries you can justify from the KB (e.g. a recording made while a request vanished outside the bridge, Q-26 — owner-walkthrough steps s1–s3 hit "no request"; that is real behaviour and should be replayed faithfully from a no-request initial state, not excused).
- Scenarios to replay (pytest-parametrized, one test per scenario + per-step detail in the report): `2026-10-05-owner-walkthrough.json`, `2026-10-05-owner-walkthrough-completion.json`, `2026-10-05-requester-ask-access.json`, `2026-10-05-owner-reads.json`, `2026-10-05-clone-seed-reads.json`, `2026-10-05-ui-walkthrough.json` (replay its HTTP exchanges), and the sandbox-relevant parts of `2026-10-05-anonymous-probes.json`. For probes on other real repos (meta-llama/Llama-3.2-1B, bigcode/starcoder, google/gemma-2-2b, mistralai/…, openai-community/gpt2, a missing repo): you may seed **local stand-in repos with the same ids** in the clone state (file names from the recordings, stub contents; gate settings and cardData as recorded) so ACC-5/ACC-6 allowlist and error probes can be replayed; compare only what the stand-in can legitimately reproduce (status, error code/message, allowlist decisions — not real file bytes), and say so in the report.
- **Rule tests** (`conformance/tests/test_rules_*.py`), each named/marked with the rule ID, for behaviour in behaviour.md that the recordings don't exercise: auto mode ask-access → accepted (DOC), form `fields` stored with labels as keys (SPEC/DOC), pagination (`limit=10`, `Link rel="next"`) (SPEC), `q` search, owner bypass (ACC-1), allowlist on demo repos (ACC-5), ACC-6 ordering, outbox effects (new request in manual → `new_request` to owner/notification email; reset → `request_reset` with reason) (DOC/§7), report contents (REP-1), control endpoints (reset restores seed; state round-trip; clock), **determinism** (run the same sequence twice from reset → identical responses and log). Separate group `test_provisional_*.py` for choices listed as provisional in open-questions.md, clearly labelled.
- **Official client driver** (`conformance/tests/test_hf_client.py`): run `huggingface_hub` against the backend — set `HF_ENDPOINT=$BACKEND_URL` **before importing** `huggingface_hub` (the access-request methods use the module constant; see docs/hf-gated/client-library.md) — e.g. in a subprocess or a session-level conftest; replicate the client's own `TestAccessRequestAPI` flow (grant → list accepted with `email is None` → cancel → reject with reason → accept again; error on same-status ops) and `auth_check` raising `GatedRepoError` for the requester, `list_*_access_requests` parsing, `update_repo_settings`.
